# RMR Platform v5.1 Role and Permissions Test Summary

## Governing rule

**RMR and Step2 administer the platform. Clients administer their businesses.**

RMR retains ownership and ultimate governance authority. Step2 has shared operational administration where authorized. Neither global role may modify client-owned CRM, forecast, activity, campaign or personnel records through ordinary support access.

## Objective permission tests

### Tenant isolation

The acceptance suite creates two tenants and proves:

- the first Client Administrator receives only the first tenant in `/api/tenants`;
- direct requests for the second tenant's Client 360 and accounts are denied;
- client navigation does not display another tenant or global portfolio functions.

Evidence: `qa/V51RC3-ACCEPTANCE-RESULTS.json`, checks 68–72; `qa/V51RC3-BROWSER-RESULTS.json`, checks 16–19.

### Client operational writes

The Client Administrator successfully creates:

- CRM account;
- contact;
- opportunity;
- activity;
- forecast version and forecast-month update.

Evidence: acceptance checks 73–80.

### RMR/Step2 read-only support

The RMR Owner can inspect client accounts and forecasts but receives a server denial when attempting to modify client-owned forecast data. The same permission architecture applies to CRM and other client-owned operating endpoints.

Evidence: acceptance checks 81–85 and support-access audit checks 118–120.

### Client access activation

The primary contact receives an invitation bound to the correct tenant and role, sets their own password, is auto-authenticated, and appears in Client 360 as an active Client Administrator.

Evidence: acceptance checks 18–20 and 55–67; browser activation evidence.

### Global administrative separation

Client browser navigation does not expose:

- Portfolio Command Center;
- other tenants;
- Partner Economics;
- global Client Pricing;
- platform system administration.

Evidence: browser checks 16–19.

## Remaining target-host permission gates

Before broad production use, repeat the role matrix on the target deployment with:

- HTTPS secure cookies;
- real SMTP invitation delivery;
- multiple real browser sessions;
- target reverse proxy;
- PostgreSQL-certified database when introduced;
- MFA after implementation;
- any future external integrations using least-privilege provider scopes.
