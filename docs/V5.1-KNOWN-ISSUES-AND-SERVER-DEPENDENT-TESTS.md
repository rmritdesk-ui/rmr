# RMR Platform v5.1 Known Issues and Server-Dependent Tests

## Candidate status

`5.1.0-commercial-cb1` is the **Windows/Docker Upgrade Reliability Correction candidate**. It is suitable for controlled RMR review and target-server pilot validation. It is not yet certified for broad, multi-node or public production use.

## Known product/integration boundaries

1. **Pilot database:** SQLite in WAL mode remains the default single-server pilot database. PostgreSQL support is not yet certified for this release.
2. **Payments:** the payment provider is mock; no real card is charged. Real authorization, settlement, refund, dispute and PCI-scope validation remain future gates.
3. **ProspectIQ:** enhancement authorization/transaction records and workflow are functional, but no live external enrichment provider is connected.
4. **Email:** SMTP/outbound email is not configured in the package. Empty/pilot installs use controlled local invitation/reset links when `RMR_LOCAL_RECOVERY_MODE=true`.
5. **MFA:** multi-factor authentication is not implemented.
6. **Social publishing:** social OAuth, platform approvals and automated publishing are not connected.
7. **Object storage/media:** uploaded training files use the persistent application data volume. Production object storage/CDN/media streaming is not connected.
8. **Domains/TLS:** custom domains, DNS, reverse proxy, automated TLS and CDN are target-infrastructure responsibilities.
9. **Accounting integrations:** actual revenue/accounting/payment feeds are not connected.
10. **Website publishing:** managed website rendering is functional. Public custom-domain publishing and production edge infrastructure remain target-server work.

## Partner Economics policy decisions intentionally pending RMR approval

The capability exists, but v5.1 does not silently decide:

- whether partner splits are calculated before or after shared operating-cost allocation;
- which labor is direct client cost, shared platform cost, partner-specific cost or RMR overhead;
- infrastructure allocation driver: equal client, active user, usage, revenue, fixed unit or another basis;
- whether general overhead affects partner settlement or only RMR management profitability;
- treatment of sales commissions relative to partner share;
- treatment of cash receipts, invoice recognition, credits, refunds and payment-processing reserves;
- which costs belong exclusively to RMR or Step2.

Until a rule is approved and effective-dated, the system keeps the cost as **policy pending** and does not include it in distributable partner settlement.

## Build-environment limitation

The local build environment used to create this candidate does not expose a Docker daemon. Therefore:

- application, API, permission, migration, backup/restore and browser workflows were executed directly;
- Dockerfiles, Compose, installer and upgrade scripts were statically validated;
- the exact ZIP still requires a real Docker installation/upgrade validation on an RMR-controlled Windows/Linux machine before Hasan handoff.

This is not represented as completed evidence.


## RC3 Windows/Docker gate

The first real RC1 Windows Docker Desktop upgrade failed because RC1 made a single host health request immediately after Docker reported the container as started. RC1 rollback successfully restored v5.0. RC2 implements bounded readiness polling, version checks, diagnostics and verified rollback, but the exact RC3 ZIP has not yet been executed on Windows Docker Desktop in the build environment. Dave's Windows upgrade test remains the release gate before Hasan handoff.

## Mandatory target-server tests

1. Verify SHA-256 checksum before extraction/use.
2. Run empty-profile install from the supported launcher.
3. Confirm Docker build, container health and restart policy.
4. Complete first-run setup; confirm exact entered owner credentials authenticate.
5. Confirm setup token cannot be reused and `INITIAL-SETUP.txt` is removed.
6. Configure HTTPS/reverse proxy and confirm secure session cookie behavior.
7. Create RMR Owner and Step2 Admin in separate sessions.
8. Create client, invite/activate Client Admin and execute tenant-isolation tests.
9. Restart Docker/host and confirm persistence.
10. Create backup, change data and restore to the prior state.
11. Execute v5.0→v5.1 Commercial Candidate upgrade on Windows Docker Desktop; retain the console transcript, `LAST-UPGRADE-RESULT.json`, and any diagnostic file; confirm notes/pricing/tenant records.
12. Confirm Windows/Linux installer transcripts and failure messages remain visible.
13. Configure disk monitoring, log rotation and off-server backup copy.
14. Validate file-upload size through the target reverse proxy.
15. Confirm domain and managed-site routes from the intended network.

## Release decision rule

A reproducible code defect must be returned to RMR and corrected in a new versioned release. Hasan/Step2 should not patch source files or database schema directly on the server.


## RC3 Windows/Docker field gate

RC2 diagnostics from the real Windows machine proved the existing v5.0 installation was operationally healthy but exposed a historical version-label mismatch: `.env` used `5.0.0-rc1` while `/api/health` returned `5.0.0-rc.1`. RC3 corrects only that known baseline mismatch and retains exact current-release validation. The exact RC3 ZIP must still pass the real Windows Docker Desktop upgrade before Hasan handoff.
