# v5.1 RC1 Windows/Docker Upgrade Failure and RC2 Correction

## Observed RC1 result

The first real Windows Docker Desktop upgrade test produced this sequence:

1. The v5.1 RC1 image built.
2. Additive migrations ran.
3. Docker reported the RC1 application container as **Started**.
4. RC1 immediately issued one PowerShell `Invoke-RestMethod` call to `http://127.0.0.1:<port>/api/health`.
5. Windows returned: **“The underlying connection was closed: The connection was closed unexpectedly.”**
6. The RC1 safety logic removed the unsuccessful RC1 container and restarted the untouched v5.0 installation.
7. Docker Desktop confirmed that v5.0 returned to normal operation.

Result:

- **RC1 Windows/Docker Upgrade Gate: FAIL**
- **RC1 Automatic Rollback/Safety Gate: PASS**

## Confirmed design defect

RC1 treated `docker compose up -d` / **container started** as if it meant **application ready**. It then made only one host HTTP request. A container can be running while its entrypoint, database migration check, reference-data verification, Python server startup, port binding, or Docker Desktop networking path is still becoming ready.

The exact low-level cause of the single closed connection cannot be proven because RC1 did not capture container state and logs before rollback. The confirmed and reproducible defect is the one-shot readiness gate and absence of failure diagnostics.

## RC2 correction

RC2 replaces the one-shot request with a bounded readiness certification process that requires all of the following:

- the Compose `app` container exists;
- the container is running and is not restarting;
- Docker health is `healthy` (or no Docker health definition exists);
- the application answers the health endpoint from inside the container;
- the application answers the health endpoint through the Windows host-mapped port;
- both responses report `status=healthy`;
- both responses report the exact expected version, `5.1.0-rc2`;
- the application maintenance status command succeeds.

The upgrade polls for up to four minutes. Transient connection resets, connection refusals and Docker `starting` health states are recorded and retried rather than treated as immediate failure.

## Failure evidence and rollback

Before any rollback, RC2 automatically creates a diagnostic file containing:

- safe environment settings with secrets omitted;
- Docker and Compose versions;
- container state, restart count and Docker health;
- host and internal health results;
- every readiness attempt;
- `docker compose ps -a`;
- application status output;
- the last 400 container log lines.

RC2 then stops/removes only its own failed container, restarts the untouched v5.0 installation, and runs the same bounded readiness validation against v5.0. The machine-readable result is written to `data/LAST-UPGRADE-RESULT.json`.

## Certification boundary

The application regression suites and RC2 upgrade logic were tested in the build environment. That environment does not expose Windows Docker Desktop, so the final Windows/Docker gate remains pending until the exact RC2 ZIP is upgraded on Dave Laughlin’s Windows Docker Desktop machine.
