# v5.1 RC2 Windows Preflight Failure and RC3 Correction

## Observed RC2 field result

RC2's preflight stopped before backup, migration or replacement because it concluded that the existing v5.0 installation was not healthy enough to upgrade. The RC2 machine-readable result recorded `rollback_status: not-required`, confirming that the upgrade had not stopped or replaced v5.0.

The diagnostic evidence showed the v5.0 container was running normally with Docker health `healthy`, exit code `0`, restart count `0`, HTTP host health `200`, internal health `healthy`, database/storage/migrations/backups healthy, and the expected pilot email limitation only.

## Root cause

The v5.0 installation contains a historical metadata inconsistency:

- `.env` declares `RMR_APP_VERSION=5.0.0-rc1`;
- the running v5.0 application reports `5.0.0-rc.1` from `/api/health`.

RC2 intentionally required exact version agreement to prevent a stale container from being certified. Because it compared those strings literally, a healthy v5.0 installation could never satisfy preflight.

## RC3 design

RC3 preserves stale-version protection while recognizing only the known v5.0 alias pair. The canonicalization function maps both `5.0.0-rc1` and `5.0.0-rc.1` to one comparable value. No general punctuation-stripping or fuzzy matching is used.

Therefore:

- expected `5.0.0-rc1`, reported `5.0.0-rc.1` -> accepted;
- expected `5.0.0-rc.1`, reported `5.0.0-rc1` -> accepted;
- expected `5.1.0-commercial-cb1`, reported `5.1.0-rc.3` -> rejected;
- expected `5.1.0-commercial-cb1`, reported `5.1.0-rc2` -> rejected.

The current-release gate remains exact. RC3 does not weaken version validation for future releases.

## Expected Windows behavior

On the same healthy v5.0 installation that RC2 rejected, RC3 preflight should accept the v5.0 health result without waiting for the 90-second timeout, proceed to create the v5.0 safety backup, stop v5.0 cleanly, copy data to the separate RC3 folder, apply additive migrations, start RC3, and certify `5.1.0-commercial-cb1` using exact current-release version matching.

If a later stage fails, the existing RC2 diagnostic and verified automatic rollback protections remain in force.
